# ncnn x86 performance research — det + rec (2026-09-26)

Workstream: ncnn performance research, **x86 host only, no device**. Everything
here was measured with the repo's own pinned fork
(`tools/build_ncnn.sh`, `FORK_PIN=b498fc07`) on a real page and a real text
line, with the app's own geometry and normalisation. The models were not
modified; the only model edits are throwaway per-class int8 copies under
`/tmp`.

Raw data: `tools/ncnn-exp/results/*.tsv`. Harness: `tools/ncnn-exp/`
(`README.md` there has the trust rules and the two measurement traps).

## Host, and what it can and cannot answer

Intel i5-8500 (Coffee Lake), 6 cores @ 3.0 GHz, AVX2 + FMA + F16C +
**AVX-VNNI**, 15.8 GB. **No AVX512, no AVX512-VNNI, no AVX512-FP16, no
AVX512-BF16.** Shared VM (other agents, an adb server, a gradle daemon).

Consequences that shape every finding below:

* **det's shipped configuration is not exercised on x86 at all.**
  `use_fp16_packed/storage/arithmetic` are *bit-identical no-ops* here (finding
  3): ncnn has no fp16 compute kernel for these layers on x86 without
  AVX512-FP16, so the "fp16 det" that ships is arithmetically **fp32** in every
  number in this document. Do not compare these milliseconds with the device's
  237-265 ms; they are different arithmetic.
* **The x86 int8 path is im2col + `vpdpbusd`** (`gemm_x86_avxvnniint8.cpp` +
  `convolution_im2col_gemm_int8.h`). The Arm path is a packed direct kernel
  using `sdot`/`vdotq_s32`. Same instruction *shape* (4 int8 MACs per lane per
  instruction), completely different data flow — which is exactly why finding 1
  matters.

Baselines on this host, quiet machine, `best_ms` = fastest iteration over
5-8 iterations x 5-7 repeats, output verified bitwise-stable:

| | config | best_ms |
|---|---|---:|
| det 896x896 | shipped (2 threads, fp16 flags on, packing on) | **255.9** |
| rec 48xW | shipped (1 thread, fp16 off, packing on) | 6.6 / 11.0 / 21.5 / 36.8 / 64.3 at W=64/128/256/432/728 |

## Findings, ranked

### 1. det int8 cannot be made worth it, and now we know why (the ceiling is 7%, and it is bandwidth, not MACs)

**Observation.** The prior rejection of det int8
(`docs/ncnn-conversion.md`: box IoU 0.61-0.89 vs a 0.95 gate, per-layer
exclusions of the 8 FPN-tail layers unhelpful) was a *quality* verdict on a
*full*-int8 build. Nobody had asked whether any single layer **class** is worth
int8-ing, nor what the speed ceiling is.

**Measurement.** Six det variants built with the repo's own
`ncnn2table`+`ncnn2int8` (KL, 10 calibration pages, `shape=[896,896,3]`), each
quantising exactly one class by deleting the other rows from the table
(`tools/ncnn-exp/subset_table.py`, driver `det_int8_variants.sh`; reproducible
end-to-end, two runs agreed within 1%). det 896x896, real page, 2 threads:

| variant | bin | min_ms | vs fp16 | max abs | **mask IoU @0.3** |
|---|---:|---:|---:|---:|---:|
| fp16 (shipped) | 4.93 MB | 255.4 | — | — | 1.000 |
| int8 all | 2.54 MB | **238.0** | **-7.2%** | 0.985 | **0.289** |
| int8 1x1 only (61 layers) | 2.60 MB | 250.3 | -2.4% | 0.997 | 0.178 |
| int8 3x3 only (3 layers) | 4.90 MB | 241.6 | -5.8% | 0.997 | 0.218 |
| int8 depthwise only (17) | 4.90 MB | 265.0 | **+3.3%** | 0.978 | 0.829 |
| int8 2x2 only (2) | 4.93 MB | 246.9 | -3.7% | 0.911 | 0.893 |
| int8 all-but-1x1 | 4.87 MB | 245.2 | -4.4% | 0.993 | 0.330 |

Two things fall out, and the second is the important one:

* **Per-class selection is worse than full int8 on quality and no better on
  speed.** 1x1-only is simultaneously the *worst* IoU (0.178) and nearly free
  (-2.4%); depthwise-only is *slower* than fp16.
* **The speed ceiling is 7.2% even with the whole graph in int8.** det's conv
  layers are 65% of layer time, so a 2-4x MAC-rate win on 65% of the work should
  have shown ~35%. It showed 7%. Per-layer efficiency explains it: on this host
  the individual conv layers run at **8-36 GMAC/s against ~96 GMAC/s of fp32
  AVX2-FMA peak** — `convrelu_1` (2x2) 8.1, `convrelu_0` (3x3 s2) 9.2,
  `convdw_160` (7x7 dw) 15.4, `convrelu_18` (3x3 s1) 36.3. The layers are
  already memory-bound on fp32 activations, so the int8 win is confined to the
  fraction of time actually spent in the MAC loop.

**Arm theory / transferability — high, and it makes the answer *more* negative.**
The mechanism is traffic, not arithmetic, so it holds on Arm. It is in fact
*worse* there: the x86 experiment compares int8 against **fp32** (a 4x traffic
advantage); Arm's det already runs **fp16 storage** (2x), so int8-over-fp16 can
at best recover half of what int8-over-fp32 recovered. The A78's `sdot`
(4 int8 MACs/lane/instr vs fp16 FMA's 8 flops/lane/instr — comparable issue
rate, and A78 has **no i8mm**, so no 8-way int8 MACs) does not change the
conclusion: the MAC loop is not the bottleneck. Verdict: **transferable, and it
closes the det-int8 question for good.** The only thing a device measurement
could still add is a *smaller* number, not a larger one.

**Cost.** Zero to keep (it is already rejected). The machinery is kept because it
is the only way to answer "would selective int8 help" again with one command.

**Where.** `tools/ncnn-exp/det_int8_variants.sh`, `subset_table.py`,
`gen_det_calib_npy.py`, `bench_variants.py`, results in
`tools/ncnn-exp/results/det_int8_variants.tsv`.

### 2. rec `use_int8_inference=false` segfaults — there is no fp32 fallback

**Observation.** The obvious "price the int8 gain" experiment for rec is to turn
int8 inference off. It does not run.

**Measurement.** `bench --model rec --set int8=0` dies with **SIGSEGV (exit
139)** at every width. `rec_dyn.bin` is an int8-packed model; the fp32 layer path
reads packed weights as floats. (This is the same failure class as the #16
double-quantization tripwire, from the other direction.)

**Arm theory.** Identical: `use_int8_inference` gates the *same* dispatch in the
same `netopt`. Portable fact, and it is a shipping constraint — any
"recover from a bad int8 model by falling back to fp32" idea is dead.

**Cost.** Zero. **Where.** `sweep.py`'s rec config list; every rec sweep row for
that config is `exit -11`.

### 3. Every `use_fp16_*` and `use_bf16_*` knob is a no-op on x86 — det's shipped fp16 config is untestable here

**Measurement** (bitwise against the baseline, 7 repeats each):

| config | det 896 | rec 432 | output |
|---|---:|---:|---|
| det: fp16_storage off | 256.2 (0.0%) | — | **bit-identical** |
| det: fp16_arithmetic off | 256.1 (0.0%) | — | **bit-identical** |
| det: all fp16 off (fp32) | 256.0 (0.0%) | — | **bit-identical** |
| rec: fp16 packed+storage+arith on | — | 36.9 (0.3%) | **bit-identical** |
| rec: fp16_packed only | — | 36.7 (0.2%) | **bit-identical** |
| rec: bf16_storage on | 285.7 (+11.5%) | 38.8 (+5.2%) | differs, maxabs 0.067 / 2.2 |

**Arm theory / transferability — the one thing here that must not be trusted.**
On Arm the same flags select real fp16 kernels (A78 has full fp16 FMA), which
is exactly why the device found fp16-on rec changing 18 lines to 17
(`docs/ocr-pipeline-perf-2026-09-25.md`). x86 has no such kernel without
AVX512-FP16, so the flags change nothing. **Do not port the x86 "fp16 is free"
result to Arm** — the device's own measurement stands. What x86 *does* give: a
clean statement that fp16 arithmetic cannot be evaluated off-device, and that
bf16 is emulated here (so its +5-11% is a *pessimistic* proxy; on A78 bf16 is
native and could plausibly win — but it fights rec's int8 path, and it changed
the output here, so it needs a device test, not a host decision).

**Cost.** Zero. **Where.** `results/sweep_det_896.tsv`,
`results/sweep_rec_widths.tsv`.

### 4. det is bandwidth-bound, and the levers that follow from that

**Observation.** The two knobs that matter for det are the two that reduce data
movement, and the two that reduce arithmetic do nothing.

| det 896 config | min_ms | vs base | output |
|---|---:|---:|---|
| shipped baseline | 255.9 | — | — |
| `use_packing_layout=0` | 414.0 | **+61.5%** | maxabs 5.7e-5, mask IoU 1.000 |
| `use_sgemm_convolution=0` | 313.0 | **+22.1%** | maxabs 2.5e-5, IoU 1.000 |
| `use_winograd_convolution=0` | 274.0 | **+6.9%** | maxabs 5.4e-6, IoU 1.000 |
| winograd F(4,3) only | 255.5 | -0.3% | **bit-identical** |
| winograd F(2,3) only / F(6,3) only | 264.4 / 263.4 | +3.2% / +2.8% | IoU 1.000 |
| `set_light_mode(false)` | 264.8 | +3.3% | bit-identical |
| `flush_denormals=0` | 256.7 | +0.3% | bit-identical |
| `use_a53_a55_optimized_kernel` | 256.5 | +0.2% | bit-identical (Arm-only knob) |
| `set_cpu_powersave(1)` | — | no effect on x86 (Android-only) | — |

**Reading.** Packing (+61%) and sgemm (+22%) are already on and are the whole
game; winograd is worth 7% and ncnn's default choice of F(2/4/6) is already
optimal (F(4,3)-only is equivalent and bit-identical, so there is no headroom in
that knob). Everything else is noise.

**Arm theory.** `use_packing_layout` is *more* important on Arm, not less: ncnn's
Arm kernels are the packed ones (fp16 `elempack=8`, int8 `elempack=16/64`) and
the unpacked fallback is a scalar loop. `use_sgemm_convolution` matters on Arm
for the same reason (1x1 -> gemm). Winograd transfers directly — ncnn's Arm
winograd F(2x2,3x3) kernel is the same transform with NEON in place of AVX2 —
but note det has only **one** 3x3 s1 layer (`convrelu_18`, 7.7%), so winograd is
a 7% lever there, not more. The `a53a55` and `denormals` rows are pure x86
no-ops and say nothing about Arm: A53/A55 kernels are a real Arm-side lever
(rec's tiny widths would run on A55s) and FTZ/DAZ is real on Arm too.

**Cost.** Zero — these are all already at their optimum. **Where.**
`results/sweep_det_896.tsv`, `results/sweep_det_winograd.tsv`.

### 5. rec thread scaling is near-linear on x86 and the device's "2/4 threads is worse" is a scheduling result

| rec, best_ms | W=64 | W=128 | W=256 | W=432 | W=728 |
|---|---:|---:|---:|---:|---:|
| 1 thread (shipped) | 6.63 | 10.96 | 21.47 | 36.78 | 64.33 |
| 2 threads | 4.20 (-37%) | 6.25 (-43%) | 11.94 (-44%) | 19.95 (-46%) | 34.51 (-46%) |
| 3 threads | 3.15 (-52%) | 4.62 (-58%) | 8.49 (-60%) | 14.31 (-61%) | 24.99 (-61%) |
| 4 threads | 3.15 (-52%) | 3.88 (-65%) | 6.93 (-68%) | 11.54 (-69%) | 21.06 (-67%) |

**All bit-identical to 1 thread** (output tensor, not just the text), at every
width. The scaling is 0.46x at 2 threads and 0.68x at 4 — worse than linear
(1.8x of 2.2x), consistent with a bandwidth-bound model, but there is no
cliff and no anomaly at any thread count.

det scales the same way, and it is the one place where x86 and the device
flatly disagree (det 896: t1 381.1, **t2 255.9 (shipped)**, t3 209.7 (-18%),
t4 196.7 (-23%), t6 190.6 (-26%), all bit-identical). The device measured t4 at
**522 ms against t2's 237-265 ms** and settled on 2.

**Arm theory — this is the finding most likely to be mis-read, so read the
caveat.** On the Pixel 7a the app measures REC_THREADS 2/4 as *worse*, and that
is consistent: (a) the device has **2 big cores** (Cortex-A78) and 4 A55s, so 4
ncnn threads put two of them on little cores; (b) the app already runs
**fanout=4**, i.e. four lines concurrently, each with 1 thread — the machine is
already saturated, so per-line threads only add contention. The x86 host has 6
identical cores and runs **one line at a time**, which is why it scales. The
x86 number says "the rec net parallelises and does not change its output"; it
says **nothing** about the right thread count for the app's fanout-4 pipeline.

What *is* worth a device test: the ordering here suggests the page-level
question was never asked — **total lines/second under fanout**, not per-line
latency. The x86 result makes it plausible that the fanout/threads pair has a
better setting than 4/1 (e.g. 2/2, or 3/1 with a core affinity hint).

**Cost.** Zero to test; the app-side change would be a constant. **Where.**
`results/sweep_rec_widths.tsv`.

### 6. rec is 80% 1x1 convolutions, and the same four layers are hot at every width

ncnn's own per-layer hook (`-DNCNN_BENCHMARK=ON`, no patch to the pinned tree)
on W=432, 1 thread, ms per extract:

| rank | layer | shape | ms | share |
|---:|---|---|---:|---:|
| 1 | `gemm_8` | [120,54] -> [13353,54] | 2.40 | 5.6% |
| 2 | `conv_75` | 1x1 [108,3,384] -> [108,3,768] | 2.20 | 5.1% |
| 3 | `conv_73` | 1x1 [108,3,384] -> [108,3,768] | 2.12 | 4.9% |
| 4 | `conv_76` | 1x1 [108,3,768] -> [108,3,384] | 2.03 | 4.7% |
| 5 | `convrelu_3` | 3x3 s2 | 1.93 | 4.5% |
| 6 | `conv_74` | 1x1 [108,3,768] -> [108,3,384] | 1.92 | 4.5% |

By class: **Convolution 79.6%** (43 layers), ConvolutionDepthWise 7.5% (14),
Gemm 6.5% (9), everything else 6.4%. The ranking is *identical* at W=64 and
W=728 (only the sizes change) — so there is one hot layer class, not a
width-dependent one. `conv_73..76` are a 384<->768 1x1 pair quartet in the last
block; each is int8 (`8=2` in the param), and at W=432 each runs at
~35 GMAC/s against ~192 GMAC/s of `vpdpbusd` peak on this CPU — **~18% of int8
peak**, which is the headroom a better 1x1 kernel would be chasing.

**Arm theory.** The structure transfers exactly: these are 1x1 convs on
flattened 3D blobs, the case the fork already had to fix once
(`bottom_blob_3d = bottom_blob_unbordered`, required by the build script's
marker gate). The Arm kernel is `sdot`-based and, like the x86 path, is
im2col-shaped. i8mm is **absent** on A78/A55, so an Arm 1x1 int8 kernel gets
4 MACs/lane/instr from `sdot` — the same width as `vpdpbusd`. The ~18%-of-peak
figure is therefore a fair estimate of the *Arm* headroom too, which makes
"write a better int8 1x1 kernel" a plausible but bounded project: at most ~1.8x
on 80% of rec, i.e. ~2.5x on rec in the limit, realistically much less.

**Cost.** A custom 1x1 int8 kernel is a real kernel project (pack/unpack
discipline, per-channel scales, fused GELU epilogue via `activation_ss`,
parity against `gemm_x86`), and it would have to be written twice (x86 + Arm) to
be worth anything. I did **not** prototype it: the honest x86 result is that
the existing path is already 4x better than the fp32 path, and the *measured*
headroom is on rec's 1x1s, not on anything structural. If it is picked up, the
Arm kernel is the one that matters and the x86 one is only the parity oracle.

**Where.** `tools/ncnn-exp/build.sh --bench` + `layerprof.py`;
`results/layers_rec_w{64,432,728}_*.tsv`.

### 7. rec's remaining knobs: sgemm is load-bearing, packing is cheap, winograd is irrelevant

| rec 432 config | min_ms | vs base | output |
|---|---:|---:|---|
| baseline | 36.78 | — | — |
| `use_sgemm_convolution=0` | 61.48 | **+67%** (W=256: +74%) | bit-identical |
| `use_packing_layout=0` | 40.75 | +11% (W=64: +3.5%) | maxabs 2.2, argmax unchanged, **text identical** |
| `use_winograd_convolution=0` | 37.06 | +0.8% | bit-identical |
| `use_bf16_storage=1` | 38.78 | +5.2% | maxabs 2.2, 1 argmax step changed (text same) |
| `set_light_mode(false)` | 38.24 | +3.9% | bit-identical |
| `flush_denormals=0` / `openmp_blocktime=0` | 36.6 / 36.8 | 0% | bit-identical |

**Arm theory.** `use_sgemm_convolution` transfers directly and is probably worth
*more* on Arm (the 1x1->gemm route is the packed one). `use_packing_layout=0`
keeping the *text* identical on x86 is a genuinely useful negative: it suggests
rec's int8 accuracy does not depend on the packed layout, so if an Arm-specific
packing problem ever appears (it has before — the SE-branch 1x1 bug in
`docs/ncnn-conversion.md`), unpacking rec is a survivable fallback. `winograd`
is irrelevant for rec by construction (one 3x3 s2, everything else 1x1) and that
transfers exactly.

**Cost.** Zero. **Where.** `results/sweep_rec_widths.tsv`.

### 8. rec at small widths is per-layer-overhead-bound, and that is a graph problem

W=64: 6.1 ms of layer time over **164 layers** = 37 us/layer, and the biggest
single layer is 0.33 ms (`gemm_8`). The model at 8 timesteps does almost no
arithmetic; what it does is walk 164 layers, each quantising, packing,
dispatching and (at 1 thread) hitting an OpenMP barrier. At W=728 the same 164
layers cost 66.1 ms, so the overhead is a *fixed* ~4-5 ms floor per line.

**Arm theory / transferability — the strongest remaining lead.** This floor is
architecture-independent: it is dispatch, packing and quantise/epilogue work,
not MACs, so it is *larger* in relative terms on the device (where a W=64 line
was measured at 10-65 ms). It scales with *lines*, and the app recognises ~18
lines per page. The fix is not a kernel: it is fewer layers per unit of work
(fuse the reshape/permute/pooling chains around SDPA, fuse quantise into the
producer's epilogue) or wider work per dispatch.

One idea I considered and rejected on the evidence: **batching several lines
into one 4-D blob**. ncnn propagates the `d` dimension through most layers, so
4 same-width lines in one extract would amortise dispatch 4x *and* make the
1x1 gemms 4x wider. But rec is **dynamic-width** by design (#23): lines in a
page have different widths, so a batch is only ever a same-width group, and the
app already gets that parallelism from `fanout=4`. It is a real option for a
"column of same-width lines" mode and not for the general case.

**Cost.** Graph surgery in the model file (`ncnnoptimize` is already built and
available; the shipped param has activations already fused as `9=1`/`9=7`, so
the remaining wins are the reshape/permute chains). Medium.

### 9. `ncnnoptimize` is a dead end on rec (it segfaults) and worth 0.6% on det (noise)

**Measurement.**

* `ncnnoptimize rec_dyn.param rec_dyn.bin out.param out.bin 0` **segfaults** and
  writes no output. The log shows 15 successful rewrites and then the crash; the
  last of them are
  `replace_convolution_with_innerproduct_after_innerproduct convrelu_5 conv_42`
  … i.e. it is rewriting the **10 SE-branch 1x1 convs**
  (`convrelu_5..9`, `conv_42/52/58/64/72`) into `InnerProduct`. Those are exactly
  the 10 layers `docs/ncnn-conversion.md` had to keep out of int8 in the early
  mixed build ("int8 1x1 on tiny 1x1-spatial SE inputs misread pack groups as
  spatial width"), on a model that is int8 throughout. Whether the crash is in
  the rewrite or in the bin serialisation is not established, but the input is an
  int8 graph and those are the layers int8 1x1 is known to mishandle, so the
  route is blocked either way.
* On **det** (fp16) the same command completes: 217 layers in, 217 out, 8
  `Convolution` -> `InnerProduct` rewrites on the SE branches after global
  pooling. Interleaved, 11 repeats: **255.6 ms -> 254.0 ms, -0.6%**, max abs
  7.45e-06, mask IoU 1.000. That is at the noise floor.

**Arm theory.** The det rewrites are `Convolution([C,1,1])` -> `InnerProduct` on
an already-tiny tensor; ncnn's Arm `InnerProduct` (a packed gemm) may be a
slightly better fit than its 1x1 conv, so a ~1% device-side win is possible — but
a 1% win is not worth rewriting 8 layers of a shipped model and re-validating
the whole detector gate. The rec crash is a property of the tool plus the int8
graph and will reproduce on any host.

**Cost.** det: low effort, no benefit, non-zero risk. rec: blocked.

**Where.** `ncnnoptimize` from the `tools/build_ncnn.sh` host leg; logs kept out
of the tree (they are two-line reproductions of the commands above).

### What will not transfer, and why, in one place

* **Anything fp16/bf16** (finding 3) — x86 has no hardware for either; the Arm
  flags select entirely different kernels. This is the largest class of
  non-transferable result in the report.
* **Thread counts as absolute numbers** (finding 5) — 6 identical host cores vs
  2 big + 4 little, and one line at a time vs four concurrent.
* **Absolute milliseconds** — det's 255.9 ms here is fp32 arithmetic; the
  device's 237-265 ms is fp16. They are not the same measurement.
* **`vpdpbusd` vs `sdot` microarchitecture detail** — same issue rate, but x86
  routes 1x1 through im2col+gemm while Arm uses a direct packed kernel, so
  "int8 is Nx on x86" does not become "int8 is Nx on Arm". The *aggregate*
  numbers (finding 1) do carry, because they are traffic-bound; the
  per-kernel numbers do not.

## The single highest-value thing to test on Arm first

**Test rec thread/fanout scheduling as a page-throughput question, not a
per-line latency question.** It is the only finding where x86 and the device
disagree in a way that suggests the device conclusion is an artefact of *how*
the work was scheduled, and it is a constant change (finding 5).

Procedure, on the Pixel 7a, no new model, no new kernel:

1. `./gradlew :app:assembleBenchmark` and install; the engine is warm after one
   page (weights are packed per Net at create time).
2. In `RecNet` creation, expose `numThreads` and the recognition `fanout` as
   system properties (both already exist as parameters: `rec_create(...,
   numThreads)` and the fanout constant in the recognition path). Sweep the
   **4 combinations that matter** on the same fixture, plus the current one:
   `(fanout, recThreads)` = (4,1) *current*, (2,2), (1,4), (8,1).
3. Measure **page wall** and **lines decoded**, not per-line extract. The
   existing log line (`recTopK w=… extract=…ms`, and `OcrEngine`'s per-line
   progress) is enough for per-line; the page number is the one that decides.
   Interleave the arms (A,B,A,B,...) with >= 8 repetitions and take the median
   of per-page walls — the same discipline as
   `docs/ocr-pipeline-perf-2026-09-25.md`. Do **not** build anything while it
   runs; on this host contention moved det by 2.5x.
4. Gate: all arms must decode 18/18 lines with the same 18 strings
   (`git diff`-free, compare the decoded text). On x86 every thread count was
   **bit-identical**, so any text change means something else moved and the arm
   is invalid.
5. Expected sign: if the device's "threads 2/4 worse" is big.LITTLE contention,
   then (2,2) should beat (4,1) — same 4-way parallelism, but each pair of lines
   shares one A78 instead of spilling onto A55s. If instead (4,1) still wins,
   the device result is real and finding 5 is x86-only, as the caveat says.
   Magnitude to beat: the doc's fanout sweep spans 543 ms (fanout4) to 1013 ms
   (fanout1) for 18 lines, so there is ~1.9x of scheduling range on the table;
   a win here is worth more than every kernel idea in this document combined
   (~30% of rec = ~17% of the page).

Second, if that comes back negative: **price det int8 on the device once**, with
`det_int8_variants.sh`'s output models, purely to confirm the 7% ceiling is also
7% there. Finding 1 predicts it will be *smaller* on Arm (fp16 baseline, not
fp32). If it comes back at 25%, finding 1 is wrong and the whole bandwidth
argument needs revisiting — that is the one experiment that could overturn this
report's main conclusion, and it costs one APK swap.

## Arm follow-up result (device): the (2,2) prediction is falsified

Tested on the Pixel 7a (`RecFanoutThreadSweepTest`, commit `ffe7a3c`;
Latin-square interleaved, 8 repeats, fresh engine per sample, text-gated) over
the full cross product `(fanout, recThreads)`:

| cell | `bookpage.png` (18 lines) | `Screenshot_20260905-093821.png` (53 lines) |
|---|---:|---:|
| 1/1 | 1118 ms | 3703 ms |
| 2/1 | 830 | 2104 |
| **4/1 (shipped)** | **610** | **1695** |
| 1/2 | 751 | 2264 |
| 2/2 (predicted winner) | **840** | **2522** |
| 4/2 | 833 | 2917 |
| 2/4 | 1644 | 6013 |
| 8/1 (no-op at batch 4) | 626 | 1933 |

**The prediction above is wrong.** `(2,2)` is 1.38x slower than `(4,1)` on
bookpage and 1.49x on quest, and the ordering is monotone in fanout and inverse
in threads — `f1t2` (751 ms, only 2-way in flight) also loses to `f4t1`
(610 ms, 4-way), so this is not big.LITTLE contention with the fanout; intra-op
threads simply lose to inter-line fanout on this part. All 128 samples decoded
identical text.

Consequences:

* finding 5's device caveat is **settled in the device's favour** — "more rec
  threads is worse" is real, and `(4,1)` is the optimum of the eight cells.
  `REC_FANOUT` now names the knob (default unchanged) so this is repeatable.
* `(8,1)` is structurally unreachable at the shipped `REC_BATCH_SIZE = 4` (a
  batch has at most four sources), so that cell is a noise floor, not a result.
* the "~1.9x of scheduling range" claim is gone: fanout 1->2->4 is the win
  (1.83x bookpage / 2.19x quest) and it is already taken.
* the remaining rec cost is per-line compute, not scheduling, so the
  **det-int8 device pricing below is now the higher-value — and only
  remaining — follow-up**.

Run conditions: 12.5 min of continuous load, battery 87 -> 82 %, thermal status
0 -> 1 (LIGHT); drift was multiplicative (~1.5 %/sample) and cancels in the
ratios (raw vs drift-normalised agree within 3 %). Resolvable floors: ~3 %
bookpage, ~15 % quest.
